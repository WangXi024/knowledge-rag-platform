# Docker Compose 部署与运维手册

> 当前实现覆盖说明（2026-08-19）：业务接口使用 `X-Tenant-ID + X-User-ID`，无 JWT；存储服务位于
> 独立 `docker-compose.storage.yml`。当前操作以根目录 `deploy/local/README.md` 为准。

## 1. 部署结论

第一期交付一个统一编排入口：

```text
compose.local.yml
```

完成首次密钥和模型配置后，使用者只需要对这一个文件执行
`docker compose up -d --build`，Compose 会构建自研镜像并一起创建自研
Gateway/Worker、RAGFlow 及两部分依赖。这里的“一个完整 Docker 部署包”是一个
Compose 项目，不是把 Docker 守护进程或多个数据库塞进一个大容器。各组件保持
独立容器，才能分别健康检查、扩容、升级、备份和恢复。

默认只有 `rag-gateway:8080` 映射到宿主机；RAGFlow、PostgreSQL、Redis、
MinIO 和 Elasticsearch 只在 `rag-backplane` 网络内可达。

## 2. 服务拓扑

| 服务 | 作用 | 持久化 | 对外端口 |
|---|---|---|---|
| `rag-gateway` | 唯一上游 REST/SSE 入口、JWT/Scope、在线 RAG | 无 | `8080` |
| `rag-worker` | 上传、解析、删除、补偿等异步任务 | 无 | 无 |
| `rag-scheduler` | 租约恢复和清理调度 | 无 | 无 |
| `rag-app-schema-check` | 启动前只读校验 DBA 已安装的 Schema 与权限 | 无 | 无 |
| `rag-app-bootstrap` | 幂等导入 Profile、创建/校验语义缓存索引 | 无 | 无 |
| `app-postgres` | 应用映射、Job、查询、引用和反馈 | Volume | 无 |
| `redis-stack` | DB 0 缓存、DB 1 RAGFlow、DB 2 Celery | Volume | 无 |
| `upload_staging_data` | Gateway/Worker/Scheduler 共享的临时上传卷 | Volume | 无 |
| `ragflow-server` | RAGFlow API、解析、检索和默认任务执行 | Logs Volume | 无 |
| `ragflow-task-executor` | 可选独立 RAGFlow Executor | Logs Volume | 无 |
| `ragflow-postgres` | RAGFlow 内部关系数据 | Volume | 无 |
| `minio` | RAGFlow 原文件/对象 | Volume | 无 |
| `elasticsearch` | RAGFlow 全文与向量检索索引 | Volume | 无 |

`ragflow-task-executor` 使用 `scaled-executor` Profile，默认不启动；当文档解析
压力需要独立扩容且固定镜像 Smoke 通过后启用。

### 2.1 公司仓库建议位置

```text
company-rag-repository/
├── services/rag-service/       # Gateway、Worker、只读 Schema Check、Dockerfile
├── deploy/                     # 落地后的完整 Compose 和环境模板
├── specs/rag-development-spec/ # 本规格包，代码实现的契约
└── vendor/ragflow/             # 可选，只读固定 Tag/子模块
```

第一期直接使用固定 RAGFlow 镜像，不修改官方源码，因此运行系统不要求把整个
RAGFlow 源码提交到公司仓库。若团队需要离线构建或审查源码，可将固定 Tag 放在
`vendor/ragflow/` 或独立镜像构建仓库，禁止混入 `services/rag-service/`。

## 3. 数据库隔离

| Database | 账号 | 使用者 | 内容 |
|---|---|---|---|
| `rag_app` | `rag_app` | Gateway/Worker | 稳定 ID、Scope、Job、配置、查询、引用、反馈 |
| `rag_flow` | `rag_flow` | RAGFlow | RAGFlow 内部 Dataset、Document、任务和元数据 |

两者使用独立容器和 Volume。Gateway/Worker 不获得 `rag_flow` 密码；RAGFlow
不获得 `rag_app` 密码。

RAGFlow v0.26.4 官方 Compose 默认数据库是 MySQL，本方案显式启用其
PostgreSQL 配置。由于当前没有历史数据，部署只执行“空 PostgreSQL 初始化 +
完整 Smoke”，不做 MySQL 迁移或双写。PostgreSQL 适配必须通过第 8 节门禁；
未通过时不得接入真实数据。

## 4. 首次启动

### 4.1 前置条件

- Docker Engine 24+、Docker Compose 2.26+。
- 生产优先 x86_64 Linux；Apple Silicon 开发机使用 Docker Desktop 的
  `linux/amd64` 兼容运行 RAGFlow。
- RAGFlow 官方最低要求 4 核、16 GiB RAM、50 GiB 可用磁盘；完整系统包含
  Elasticsearch、PostgreSQL 和统一 Redis Stack，实际需要额外余量。
- `vm.max_map_count >= 262144`。
- 可访问固定镜像仓库、上游 JWKS/公钥和模型服务。
- 仓库根目录存在可构建自研 Gateway/Worker 的 `Dockerfile`。

Apple Silicon 约束：

- `.env.full` 设置 `RAGFLOW_PLATFORM=linux/amd64`，只作用于
  `ragflow-server` 和 `ragflow-task-executor`。
- 禁止全局设置 `DOCKER_DEFAULT_PLATFORM=linux/amd64`，避免把本可原生运行的
  自研服务、PostgreSQL、Redis 等全部切到模拟模式。
- 自研镜像默认构建为宿主机 ARM64；它可以通过 Compose 网络调用 amd64 模拟
  容器。
- 若出现 illegal instruction、进程异常退出或解析显著异常，先标记为
  `ARCH_EMULATION`，不得误判为 PostgreSQL 兼容问题。正式 ARM64 部署只能使用
  自建且通过全链路 PoC 的固定 RAGFlow 镜像。

### 4.2 配置

```bash
cd rag-development-spec/deploy
cp .env.full.example .env.full
```

替换所有 `change-me`，并将生产镜像从 Tag 固定为审核过的 Digest。JWT 密钥
配置二选一：

- 在线环境：`AUTH_JWKS_URL=https://.../.well-known/jwks.json`；
- 离线环境：清空 JWKS URL，将只读公钥挂载进 Gateway/Worker，并设置
  `AUTH_PUBLIC_KEY_PATH`。

运行预检：

```bash
./preflight.sh
```

模型服务可以是公司/云端 OpenAI-compatible API，也可以是运行在 macOS 宿主机
的 Ollama。宿主机服务从容器内使用
`http://host.docker.internal:<port>/v1`；必须显式允许 Docker Desktop 访问，
并分别配置 Gateway 的 LLM/语义缓存 Embedding 与 RAGFlow 的
Embedding/Reranker Provider。两侧可以使用同一模型服务，但仍是两个配置入口。

开发阶段允许使用测试私钥签发 JWT，Codex 必须提供
`tools/generate_dev_keys.py` 和 `tools/issue_dev_token.py`；生成的私钥及
`.env.full` 不得提交 Git。真实运行至少需要：

- `AUTH_AUDIENCE`、JWKS URL 或离线公钥；
- Gateway 使用的 LLM、Rewrite 和语义缓存 Embedding；
- RAGFlow 使用的 Embedding、Reranker 和 API Key。

缺少真实模型时可以完成 Mock/Fake 自动测试，但不得把真实问答标记为已验证。

### 4.3 一条命令启动

```bash
docker compose --env-file .env.full -f docker-compose.full.yml up -d --build
```

该命令会按健康依赖顺序启动存储、RAGFlow、应用迁移、`rag-app-bootstrap`、
Gateway 和 Worker。Bootstrap 从镜像 `/app/configs` 幂等导入 Profile，并创建
或校验 Redis Stack 语义缓存索引；任一必需 Profile 缺失或同版本 checksum
冲突时，Gateway/Worker 不得启动。

它不会自动创建 RAGFlow API Key 或模型 Provider，这两项需要在首次初始化后
完成一次受控配置。

### 4.4 首次 RAGFlow Bootstrap

默认不把 RAGFlow UI/API 映射到宿主机。仅在本机首次 Bootstrap 时，可以临时
停止常驻 Server，并启动一个只绑定 `127.0.0.1` 的一次性实例：

```bash
docker compose --env-file .env.full -f docker-compose.full.yml stop ragflow-server
docker compose --env-file .env.full -f docker-compose.full.yml run --rm \
  -p 127.0.0.1:8081:80 -p 127.0.0.1:9381:9380 ragflow-server
```

浏览器只在本机打开 `http://127.0.0.1:8081`，完成：

1. 初始化管理员并登录 RAGFlow。
2. 配置 Embedding、Reranker、可选 LLM 和 MinerU Provider。
3. 创建仅供 Gateway/Worker 使用的 RAGFlow API Key。
4. 将 Key 写入 Secret 管理系统或 `.env.full`。
5. 结束一次性实例，并重新执行统一 `up -d --build`；确认临时端口消失、外部只能访问
   Gateway。

禁止把 RAGFlow API Key 当作上游 JWT，也禁止对业务网络长期开放 RAGFlow。

### 4.5 验证

```bash
./smoke.sh
docker compose --env-file .env.full -f docker-compose.full.yml ps
```

随后使用两个不同 Scope 的测试 JWT，分别创建知识库并验证交叉访问返回 404。
第一期不附带业务测试数据；团队使用自有文件手动验证上传、解析、检索、回答、
引用、语义缓存和删除。

上传验证必须确认：

1. Gateway、Worker、Scheduler 都挂载 `upload_staging_data` 到
   `/var/lib/rag/uploads`。
2. Gateway 先写 `.uploading`，完成后原子发布 `.ready`。
3. Worker 在另一个容器中能读取同一 `staged_file_id` 并上传 RAGFlow。
4. 成功后暂存文件删除；失败文件按 TTL 保留并由 Scheduler 清理。
5. 暂存卷写满、文件丢失、Hash 不一致时返回稳定错误且不盲目重传。

## 5. 启停和查看状态

```bash
# 查看状态
docker compose --env-file .env.full -f docker-compose.full.yml ps

# 查看单个服务日志
docker compose --env-file .env.full -f docker-compose.full.yml logs -f rag-gateway

# 停止但保留数据
docker compose --env-file .env.full -f docker-compose.full.yml down

# 拉取并启动审核后的新镜像
docker compose --env-file .env.full -f docker-compose.full.yml pull
docker compose --env-file .env.full -f docker-compose.full.yml up -d --build
```

不得在日常操作中使用 `down -v`；它会删除持久化 Volume。确需清空仅含 PoC
数据的环境时，必须先确认目标 Compose 项目和备份，再单独批准。

启用独立 Executor：

```bash
docker compose --env-file .env.full -f docker-compose.full.yml \
  --profile scaled-executor up -d
```

## 6. 健康与降级

- `/health/live` 只检查 Gateway 进程。
- `/health/ready` 检查 App PostgreSQL、统一 Redis Stack 和 RAGFlow；依赖未就绪返回
  503。它还必须确认必需 Profile 已导入、Redis Stack 索引定义和
  Embedding 维度一致、上传暂存卷可写。
- DB 0 缓存操作失败可绕过缓存；统一 Redis Stack 整体故障还会影响 Celery 和
  RAGFlow，Ready 必须返回不可用。
- RAGFlow/Elasticsearch 故障：检索和问答不可用，返回稳定 503；不能绕过权限
  或返回未验证旧缓存。
- LLM 故障：纯检索仍可用；回答按 Model Profile 有限降级。
- JWKS 暂时不可用：只允许在缓存有效期内使用已验证 Key；Key 过期后 fail
  closed，不接受无法验证的 JWT。

## 7. 密钥与网络

至少管理：JWT 验证公钥/JWKS、RAGFlow API Key、两个 PostgreSQL 密码、一个
Redis Stack 密码、Elasticsearch 密码、MinIO 密码、Embedding/Reranker/LLM/MinerU
凭据。

- `.env.full` 不提交 Git，不打入镜像。
- 生产使用 Secret Manager/Kubernetes Secret 或等效机制。
- 日志不得记录 Authorization、原始 Claim、数据库 DSN 或模型 Key。
- 轮换采用“新增 -> 双 Key 窗口 -> 更新服务 -> 验证 -> 吊销旧 Key”。
- 内部服务不发布宿主机端口；若部署平台支持，再用安全组/NetworkPolicy 限制。

## 8. 首期部署验收门禁

- [ ] `docker compose config` 可解析，服务和 Volume 完整。
- [ ] 自研镜像由 Compose `--build` 构建，Migration 和 Bootstrap 均成功退出。
- [ ] 必需 Profile 导入幂等；同版本不同 checksum 会阻止启动。
- [ ] Redis Stack 索引字段、维度和模型与配置一致。
- [ ] Gateway/Worker 跨容器共享暂存文件，成功清理和失败 TTL 清理通过。
- [ ] Apple Silicon 环境只模拟 RAGFlow 容器，并记录架构相关日志/结果。
- [ ] `ragflow-postgres` 空库完成初始化，日志无 MySQL 连接尝试。
- [ ] RAGFlow 创建/删除 Dataset、上传/解析/列 Chunk/检索/删除通过。
- [ ] RAGFlow 和全部依赖重启后数据仍可用。
- [ ] Gateway 迁移成功，`/health/live`、`/health/ready` 正常。
- [ ] 除 Gateway 外无宿主机端口。
- [ ] 无 JWT、伪造/过期 JWT 被拒绝；两个 Scope 交叉访问全部 404。
- [ ] Redis Stack DB 0 中语义缓存带 `security_scope_id` 过滤，跨 Scope 不命中。
- [ ] 所有镜像记录 Tag、Digest、来源和许可证。

RAGFlow PostgreSQL PoC 报告必须分别记录数据库、RAGFlow API、模型/存储依赖
和 Apple Silicon 架构模拟四类结果。若 PoC 失败，保持 Gateway API 和应用
PostgreSQL 不变，
在尚未接入真实数据前评估把 RAGFlow 内部库回退到固定版本官方默认 MySQL。
不得通过修改 RAGFlow 内部业务表绕过初始化错误。

## 9. 备份与恢复

| 数据 | 备份方式 |
|---|---|
| App/RAGFlow PostgreSQL | 每日 `pg_dump`；生产按 RPO 使用快照/WAL |
| MinIO | Bucket 版本、快照或跨存储复制 |
| Elasticsearch | Snapshot Repository |
| Compose/Profile/Prompt | Git 与发布制品 |
| Redis | AOF 供短期恢复；队列事实仍以 PostgreSQL 为准 |
| Upload Staging | 不备份；由 Job/上游幂等重传恢复 |

恢复顺序：PostgreSQL -> MinIO/Elasticsearch -> RAGFlow -> 应用 Redis ->
Gateway/Worker -> 映射对账 -> Smoke -> 两 Scope 隔离复测。只恢复 PostgreSQL
不能恢复原文件和检索索引。

## 10. 发布、升级与回滚

- 固定通过 PoC 的 RAGFlow v0.26.4 Tag 和镜像 Digest，不跟随 `nightly`。
- 非必要不合并上游更新；需要升级时在独立分支/环境比较 Release Note、API、
  Compose、数据库迁移和解析器变化。
- 升级前备份数据库、MinIO 和 Elasticsearch，并运行 Adapter Contract 与
  完整 Smoke。
- 应用数据库使用先扩展后收缩迁移，先迁移再滚动 Gateway/Worker。
- 回滚优先恢复旧应用镜像和旧 RAGFlow 环境；不可逆迁移必须提前声明恢复点。
- 若未来 Fork RAGFlow，内部改动保持小而独立，维护补丁台账，按需逐项重放到
  新稳定 Tag，禁止生产分支直接 `git pull`。

## 11. 常见故障

| 现象 | 首要检查 | 处置 |
|---|---|---|
| Gateway Ready 失败 | App DB/Redis/RAGFlow Health | 恢复依赖，不绕过 Ready |
| RAGFlow 尝试 MySQL | `DB_TYPE`、挂载模板、所有进程环境 | 修正 PostgreSQL 配置后在空库重试 |
| 上传长期停留 | Worker Job、RAGFlow 文档、孤儿映射 | 执行幂等核对和补偿，禁止盲目重传 |
| Worker 找不到上传文件 | 三个服务的 Volume、`.ready`、Job `staged_file_id` | 恢复共享挂载；校验 Hash，不能改用容器私有 `/tmp` |
| Bootstrap 失败 | Profile checksum/必需引用、Redis 索引维度 | 新增 Profile/索引版本，禁止覆盖历史版本或现场改索引 |
| Apple Silicon 进程退出 | `platform`、Docker Desktop 模拟、容器日志 | 归类架构问题；必要时换 x86_64 环境或自建 ARM64 镜像 |
| 解析失败 | Parser Provider、RAGFlow Task、资源 | 保留错误码，按策略有限重试或手动换 Profile |
| 检索为空 | READY、Chunk、Embedding/Profile | 比较项目 Retrieval 与 RAGFlow 原始结果 |
| 语义缓存异常 | Scope Tag、revision、阈值、引用状态 | 强制未命中并走正常 RAG |
| SSE 中断 | 代理缓冲/超时、取消标记、LLM | 禁用缓冲，检查 request_id 和阶段耗时 |
| Elasticsearch 磁盘水位 | Volume、索引状态 | 扩容/清理后验证索引，不手工改业务文档映射 |
