# RAG 系统需求与范围说明

> 当前实现覆盖说明（2026-08-19）：运行时临时使用 `X-Tenant-ID + X-User-ID` 的
> Direct Identity 模式，
> 不执行本文件描述的 JWT 验签。JWT/JWKS 内容是未来生产 Identity 目标；当前 API
> 以 `../openapi/rag-api-v1.yaml` 为准。

> 版本：1.4.0  
> 阶段：第一期开发基线  
> 目标：定义为什么建设、第一期解决什么、明确不解决什么，并为设计、接口和测试提供可追踪需求

## 1. 项目背景

本项目建设一个独立部署的 RAG 服务。上游业务系统通过稳定的 REST/JSON 和 SSE API 完成知识库管理、文档接入、检索和问答；RAG 服务内部通过 RAGFlow 完成文档解析、Chunk、Embedding、索引、混合检索和 Rerank，自研 RAG Gateway/Worker 完成接口稳定化、任务编排、Context、LLM、引用校验、缓存和资源范围隔离。

第一期面向内部可信上游系统，不面向最终用户直接开放。上游仍然是用户、组织、角色和业务权限的权威来源；RAG 系统必须验证上游签发的安全声明，并保证不同安全范围的数据不能互相访问或命中缓存。

## 2. 建设目标

1. 提供与 RAGFlow 内部模型解耦的稳定 RAG API。
2. 完成知识库、文档、解析任务、纯检索、非流式和流式问答闭环。
3. 对回答提供可定位 Citation，并在证据不足时拒答。
4. 实现精确缓存和语义缓存，文档或配置变化后旧缓存不能命中。
5. 实现第一期最小安全隔离，用户 A 的资源不会被不同 Scope 的用户 B 查看、检索或缓存复用。
6. 提供一个统一 Docker Compose 入口，一条命令启动自研服务、RAGFlow 及全部基础设施。
7. 提供工程测试和手动验收能力；真实业务测试数据和质量标注由使用方后续提供。

## 3. 调用方与典型场景

### 3.1 调用方

- 上游业务后端：认证最终用户、决定用户当前租户/Workspace/业务范围并签发短期 JWT。
- 运维人员：部署、配置、查看健康状态和处理故障。
- 开发与测试人员：通过 API 上传测试文档、检查 Chunk、检索、问答和引用。

最终用户不得直接持有 RAGFlow API Key，也不得绕过上游业务系统直接访问 RAGFlow。

### 3.2 典型场景

1. 上游为当前用户签发带 `rag_scope_id` 的 JWT，调用 RAG API 创建知识库。
2. 上游上传文档并轮询 Job，文档经过解析、切分、向量化和索引后进入 `READY`。
3. 上游在当前 Scope 的知识库中执行纯检索或 RAG 问答。
4. Gateway 构建 Context、调用 LLM、校验 Citation 并返回答案。
5. 相同或语义相似的问题在严格相同 Scope、知识库 revision 和配置版本下命中缓存。
6. 其他 Scope 请求同一资源时返回 404，且不得调用 RAGFlow、Embedding 或 LLM。

## 4. 安全范围模型

上游 JWT 至少包含：

| Claim | 用途 |
|---|---|
| `iss` | 令牌签发方 |
| `aud` | 必须包含 `rag-service` |
| `sub` | 上游用户或服务主体标识 |
| `tenant_id` | 上游租户标识 |
| `rag_scope_id` | 当前请求的 RAG 数据隔离范围 |
| `exp` | 过期时间 |
| `jti` | 令牌唯一标识，供安全排障使用 |

RAG Gateway 校验签名、算法、`aud`、`exp` 和必需 Claim 后生成不可修改的 `SecurityContext`。数据库中的 `security_scope_id` 使用以下输入的规范化 Hash，避免把原始租户和 Scope 标识作为索引键：

```text
SHA-256(tenant_id + "\\x1f" + rag_scope_id)
```

第一期每个资源只属于一个 `security_scope_id`。私有知识库应使用用户独立 Scope；需要共享时，由上游为被授权用户签发相同 Workspace Scope。RAG 系统不决定谁应该进入某个 Scope，只验证并执行已签名的 Scope。

## 5. 第一期功能需求

| ID | 需求 | 验收依据 |
|---|---|---|
| FR-KB-001 | 创建、列表、详情、修改和异步删除知识库 | OpenAPI + KB API 测试 |
| FR-DOC-001 | 单文档流式上传、共享暂存、Hash、状态查询、解析、重解析、安全版本更新、回滚、重试和删除 | 文档/版本/Job/跨容器暂存测试 |
| FR-RET-001 | 在一个或多个当前 Scope 知识库内执行混合检索 | Retrieval E2E |
| FR-ANS-001 | 提供非流式和 SSE 流式 RAG 问答 | Answer/SSE E2E |
| FR-CIT-001 | 回答引用可定位到文档、页码/坐标和原文摘录 | Citation 测试 |
| FR-REF-001 | 无证据或引用校验失败时返回受控拒答 | 拒答测试 |
| FR-CACHE-001 | 实现精确缓存和语义缓存，故障时绕过 | Cache 测试 |
| FR-IDEM-001 | 创建、上传、触发任务、删除和反馈支持幂等 | 幂等并发测试 |
| FR-SEC-001 | 验证上游 JWT 并生成 SecurityContext | JWT 测试 |
| FR-SEC-002 | 所有外部可寻址资源按 `security_scope_id` 过滤 | Scope 测试 |
| FR-SEC-003 | 跨 Scope 资源访问返回 404 且不调用下游 | 越权 E2E |
| FR-SEC-004 | 精确/语义缓存和幂等记录不得跨 Scope 命中 | Cache/幂等测试 |
| FR-DEP-001 | 单一 Compose 入口启动完整系统，只暴露 Gateway | Compose 校验 + Smoke |
| FR-CFG-001 | Profile YAML 经 Bootstrap 幂等导入数据库；同版本内容冲突时阻止启动 | Bootstrap 测试 |
| FR-DEP-002 | Apple Silicon 仅对 RAGFlow 使用 amd64 兼容模式，自研镜像原生构建 | Compose/架构预检 |

## 6. 第一期非功能需求

| ID | 要求 |
|---|---|
| NFR-API-001 | 对外契约以 OpenAPI 3.1 为第一事实来源，`/v1` 内保持向后兼容 |
| NFR-SEC-001 | 只接受批准的 JWT 非对称签名算法，拒绝 `none` 和调用方自报身份头 |
| NFR-SEC-002 | 跨 Scope 数据泄露验收用例必须全部通过 |
| NFR-REL-001 | PostgreSQL 是 Job 状态事实来源，Redis 消息丢失可恢复 |
| NFR-REL-002 | 缓存、Reranker 等可降级组件故障不得扩大为不可控级联故障 |
| NFR-OBS-001 | 第一期开启结构化日志、`request_id`、`job_id`、稳定错误码和关键阶段耗时 |
| NFR-TEST-001 | Domain/Application 核心分支覆盖率目标不低于 80%，安全关键路径逐场景断言 |
| NFR-DEP-001 | 有状态服务使用独立持久卷，镜像生产部署固定 Digest |
| NFR-REL-003 | 上传暂存以 `.uploading -> .ready` 原子发布，Worker 只消费完整文件 |
| NFR-PRIV-001 | 默认不记录 Authorization、完整文档、完整 Prompt 和完整 Context |

具体容量、P95、RPO 和 RTO 由目标环境和真实数据确定；第一期文档只给出测量方法，不作脱离环境的生产承诺。

## 7. 第一期负责

- 自研 RAG Gateway、RAG Worker、Scheduler 和应用 PostgreSQL。
- RAGFlow 固定版本的部署、配置、公开 API 适配和契约测试。
- 知识库、文档、Job、检索、问答、引用和反馈 API。
- Query Rewrite、检索编排、结果标准化、Context Pack、LLM 和 SSE。
- 引用校验、无依据拒答、精确缓存和语义缓存。
- JWT 验证、SecurityContext 和 `security_scope_id` 强制隔离。
- 基础日志、稳定错误码、有限重试、降级和故障恢复。
- 单元、API、数据库、Adapter 契约、最小集成和手动 Smoke 测试。
- 一个完整 Docker Compose 部署包。
- 共享上传暂存卷、Profile/Redis 索引 Bootstrap 和过期暂存清理。

## 8. 第一期明确不负责

- 用户注册、登录、密码、验证码和用户资料。
- 组织、角色、用户组、Workspace 成员和复杂 ACL 的管理。
- 判断某个用户为什么可以获得某个 `rag_scope_id`。
- Source Authority、业务 DocumentVersion、IndexGeneration 和 Tombstone。
- 外部数据源注册、同步游标和数据源治理。
- Agent、MCP、GraphRAG 和外部高风险动作。
- 独立管理前端。
- 真实业务测试文档、参考答案、人工标注和黄金评测数据集的提供。

## 9. 第一期延期建设

- 多 Scope 并集访问、资源授权分享和复杂 ACL 表达式。
- PostgreSQL Row-Level Security；第一期通过强制 ScopedRepository 和完整测试保证。
- 自动化 RAG 质量评测流水线、评测 API、A/B 实验和评测报告。
- 完整 OpenTelemetry 分布式 Trace、Prometheus/Grafana Dashboard 和自动告警。
- 生产级大规模压力、容量和混沌平台。
- RAPTOR、完整 GraphRAG 和 HyDE 的默认启用；当前只实现 Gateway 侧车
  Parent-Child、抽取式摘要和轻量实体关系导航，不等同于上述完整算法。

## 10. 外部依赖与假设

- 上游能够签发短期 JWT，并提供 JWKS URL 或离线公钥。
- 上游保证 `tenant_id` 和 `rag_scope_id` 的语义正确、稳定且不可由最终用户自行选择。
- RAGFlow、Embedding、Reranker 和 LLM 的固定版本/模型可用。
- 模型可以是公司/云端 OpenAI-compatible API，也可以是宿主机 Ollama；外部
  模型未配置时只能完成 Mock/Fake 测试，不能完成真实问答验收。
- 生产环境提供域名、TLS 终止、Secret 管理、备份位置和告警接收人。
- RAGFlow PostgreSQL 部署必须在空库完成 PoC；未通过前不得写入真实业务数据。

## 12. 第一期完成定义

只有满足以下条件才可宣布第一期完成：

1. 规格包校验通过，OpenAPI、DDL、配置和 Compose 均可解析。
2. 从空环境可以用统一 Compose 启动完整系统。
3. 知识库创建、文档上传解析、检索、问答、引用和删除闭环通过。
4. JWT、跨 Scope 资源、缓存和幂等隔离用例全部通过。
5. 依赖故障不会造成无界重试或跨 Scope 降级。
6. 使用方可以用自己的文档完成手动验收。
