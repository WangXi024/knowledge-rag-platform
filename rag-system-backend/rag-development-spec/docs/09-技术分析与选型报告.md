# 技术分析与选型报告

> 当前实现覆盖说明（2026-08-19）：运行时暂用 Direct Tenant/User Header；JWT/JWKS 仍是
> 推荐的未来生产方案，不是当前已启用能力。

## 1. 结论

第一期采用：

```text
自研 RAG Gateway / Worker
    + RAGFlow v0.26.4（公开 API 集成，不修改官方源码）
    + PostgreSQL 18.4（应用库与 RAGFlow 库隔离）
    + Elasticsearch 8.11.3（由 RAGFlow 管理）
    + Redis + Redis Stack（任务控制、精确缓存和语义缓存）
    + Docker 命名 Volume（Gateway/Worker 上传暂存）
    + MinIO（由 RAGFlow 管理）
    + OpenAI-compatible 模型服务
```

RAGFlow 负责复杂文档解析、Chunk、Embedding 编排、索引、混合检索和 Rerank；
自研层负责稳定 API、JWT/Scope 隔离、任务状态、检索编排、Context、生成、引用
验证和缓存。第一期不 Fork RAGFlow。

## 2. RAG 框架对比

| 维度 | RAGFlow | LlamaIndex | Haystack |
|---|---|---|---|
| 形态 | 完整 RAG 平台/服务 | Python RAG 开发框架 | 显式组件 Pipeline 框架 |
| 复杂文档解析 | 强，内置 DeepDoc/MinerU 等路径 | 依赖 Reader/外部解析服务 | 通常组合外部 Converter |
| 开箱即用入库/检索 | 高 | 中，需要自组服务 | 中，需要自组 Pipeline |
| 中文资料和实践 | 相对丰富 | 通用生态丰富 | 相对较少 |
| API 服务化 | 自带公开 API | 需要自研 | 需要自研 |
| 深度代码可控性 | 中 | 高 | 高 |
| 第一期开工速度 | 最高 | 中 | 中 |
| 主要风险 | 部署重、内部模型变化、API 版本差异 | 自研模块多、质量依赖组合 | 学习/组件整合成本 |

选择 RAGFlow 的原因是当前项目最需要快速获得复杂文档解析和完整检索链路，
同时由 Gateway 隔离其不稳定 API。LlamaIndex 适合作为未来需要完全自研检索
服务时的首选 Core；Haystack 适合团队特别重视显式 Pipeline 和强组件边界的
场景。第一期同时引入多个框架会增加重复抽象和排障面，不采用。

## 3. 存储选型

### 3.1 向量与全文索引

| 方案 | 成本/许可 | 国内可用性 | 性能与能力 | 与当前方案 |
|---|---|---|---|---|
| Elasticsearch | 可自建；需审查对应版本许可 | 成熟，运维人才多 | BM25、过滤、向量/混合检索一体 | 推荐，RAGFlow 默认链路成熟 |
| OpenSearch | Apache 2.0，自建友好 | 可用 | 全文与向量一体 | 可作 ES 替代，但需单独 RAGFlow 兼容验证 |
| Milvus | 开源，自建 | 国内生态强 | 大规模向量检索强 | 数据量/向量 QPS 明显增大后再评估 |
| Qdrant | 开源/商业云 | 可自建 | 易用、过滤与向量性能好 | 不是当前 RAGFlow v0.26.4 的低风险默认 |
| pgvector | PostgreSQL 扩展 | 易部署 | 中小规模简单，但全文融合需额外设计 | 不替代当前 RAGFlow 索引 |

第一期使用 Elasticsearch 同时承担 RAGFlow 的全文与向量索引，减少“双写、
双检索、融合一致性”问题。Milvus 技术上可通过修改/扩展 RAGFlow 的存储适配
实现，但会进入官方源码二次开发和升级冲突，不属于第一期。

### 3.2 关系数据库

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| PostgreSQL | 事务/JSONB/组合约束强，团队统一技术栈 | RAGFlow 官方 Compose 默认不是它，需 PoC | 应用库确定采用；RAGFlow 内部库有条件采用 |
| MySQL | RAGFlow 固定版本官方默认路径 | 与本项目数据库栈分裂 | 仅作为 RAGFlow PostgreSQL PoC 失败时回退 |

应用库必须 PostgreSQL。RAGFlow 内部库在无历史数据阶段验证 PostgreSQL；如果
完整生命周期不通过，保持 Gateway API 不变并回退 RAGFlow 官方默认 MySQL，
优先保证系统可交付性。

### 3.3 缓存与对象存储

| 能力 | 选择 | 原因 |
|---|---|---|
| Celery/取消状态 | Redis Stack DB 2 | 统一物理实例，Key 与缓存/RAGFlow 分区 |
| 精确/语义缓存 | Redis Stack DB 0 | 同时支持 TTL KV 和向量相似检索 |
| RAGFlow 内部缓存 | Redis Stack DB 1 | 应用不得扫描或修改该 DB |
| 原文对象 | MinIO | RAGFlow 支持且适合自建 |

DB 0、1、2 只隔离 Key，不隔离资源与故障。当前选择优先降低本地/小规模部署成本；
生产达到容量、性能或权限拆分阈值时，优先将 Celery 拆回独立 Redis。

## 4. 采用与自研边界

| 能力 | 采用方式 | 责任组件 |
|---|---|---|
| 文档解析、Chunk、Embedding 编排 | 直接采用并配置 Profile | RAGFlow |
| 全文/向量索引、混合检索、Rerank | 直接采用并通过 Adapter 标准化 | RAGFlow + ES |
| 稳定 REST/SSE、JWT/Scope、幂等、Job | 自研 | Gateway/Worker/App PostgreSQL |
| Query Rewrite、Context Pack、LLM | 自研编排 | Gateway |
| Citation Verification、拒答 | 自研，不修改 RAGFlow | Gateway |
| 精确缓存、语义缓存 | 自研 | Gateway + Redis Stack |
| 用户/组织/复杂 ACL | 不负责 | 上游系统 |
| 自动评测/完整观测平台 | 后续 | 独立建设 |

## 5. 风险和触发条件

| 风险 | 第一阶段处理 | 触发替代方案的条件 |
|---|---|---|
| RAGFlow API/响应变化 | 固定 Tag、Adapter、Fixture | 稳定 API 无法完成硬需求 |
| RAGFlow PostgreSQL 不完整 | 空库全生命周期 PoC | 初始化/升级/恢复阻断则内部库回退 MySQL |
| Apple Silicon 镜像架构 | 仅 RAGFlow 使用 amd64 模拟并单独记录 PoC | 解析/稳定性不通过则改用 x86_64 Linux 或自建 ARM64 镜像 |
| 容器间上传文件不可见 | 共享命名卷、原子 ready、Job 仅保存 staged ID | 多节点部署时替换为临时对象存储实现 |
| Profile/缓存索引漂移 | 启动 Bootstrap 校验 checksum、Schema 和向量维度 | 不一致时创建新版本，禁止现场覆盖 |
| ES 容量不足 | 监控磁盘/Heap，容量评估 | 向量规模/QPS达到实测瓶颈后评估 Milvus |
| 解析质量不满足 | DeepDoc/MinerU Profile 与 Reparse | 多数核心文档均无法满足时评估外置解析 Pipeline |
| 深度定制需求 | Gateway 外围扩展 | 必须改 RAGFlow 核心数据模型/检索链路时评估 Fork 或 LlamaIndex Core |

## 6. 版本策略

- 固定已通过 PoC 的 RAGFlow v0.26.4 镜像 Digest，不使用 `latest`/`nightly`。
- 第一阶段只调用公开 API，不修改官方源码。
- 上游更新非必要不拉取；必须升级时在独立环境处理差异、运行 Contract/Smoke，
  通过后再发布。
- 只有稳定 API 无法实现已确认硬需求时才评估 Fork；Fork 后内部 Commit 保持
  小、独立、可重放，并维护补丁台账。
