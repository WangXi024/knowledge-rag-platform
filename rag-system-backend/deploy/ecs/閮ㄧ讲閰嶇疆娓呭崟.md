# GitHub、ECS 环境变量与数据库迁移清单

本清单用于 LazyTT RAG 后端的 ECS Docker Compose 部署。按当前
[workflow](../../.github/workflows/ecs.yml)、[Compose](../../compose.dev.yml)、
[环境模板](.env.dev.example) 和 [发布工具](release.py) 核对，整理日期为 2026-09-07。

当前只实现 `dev` 环境：Compose 项目名为 `lazytt-rag-ecs-dev`。默认服务目录是
`/opt/lazytt/lazytt-rag-system`，ECS 上的常驻文件统一叫 `compose.yml`；配置多个 GitHub Environment
本身不会让当前代码自动支持 staging 或 production。这里只覆盖后端。

| 内容 | 配置位置 | 数量与职责 |
|---|---|---|
| GitHub Variables | 仓库级 Actions Variables | 6 项，控制是否发布及连接哪台 ECS |
| GitHub Secrets | 仓库级 Actions Secrets | 2 项，用于 SSH 身份和主机校验 |
| Compose 运行配置 | ECS `/etc/lazytt/rag.env` | 70 项（含可选 MinerU 配置），供容器及发布工具读取 |
| 镜像与构建信息 | 发布参数或可选环境值 | 3 项，见第 2.12 节 |
| 数据库迁移 | 自研应用镜像内 `/app/migrations` | 4 个 SQL 文件，按当前数据库状态显式选择 |

所有 `<…>` 都表示待填写信息，不能原样用于正式发布。本文不包含真实密码、私钥或 API Key。
当前 ECS 的真实连接、权限、模型调用及容量仍需在目标服务器验收。

第 1～3 节记录当前代码可用的配置和命令；第 4 节是本次新增的目标流程：流水线统一
交付文件，等待管理员完成数据库变更，验收通过后继续发布。第 4 节尚需修改 workflow
和交付/验收入口才能生效，不能视为当前流水线已经具备的行为。

## 1. GitHub Secrets 与 Variables

### 1.1 仓库级 Variables

在仓库的 **Settings → Secrets and variables → Actions → Variables** 中逐项添加。
值直接填写，不加 Bash 的 `export` 或包裹引号。配置入口参见
[GitHub Variables 官方说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-variables)。

| 名称 | 填写值 | 用途与填写要求 |
|---|---|---|
| `ECS_DEPLOY_ENABLED` | `false` | 首次先关闭 push 自动发布；首次流程验收后改为 `true`。开关只控制 `dev` push，不阻止手动选择 `release` |
| `ECS_HOST` | `<ECS_SSH_HOST>` | GitHub Runner 可达的 SSH IP/域名，不带协议、端口或路径 |
| `ECS_USER` | `root` | 当前脚本无 sudo，要求该账号能直接读取 root 专属配置及执行 Docker；须与服务器实际允许的 SSH 身份一致 |
| `ECS_PORT` | `22` | SSH 实际端口；未配置时 workflow 默认 22 |
| `ECS_REPO_DIR` | `/opt/lazytt/lazytt-rag-system` | 独立服务目录，最终文件为此目录下的 `compose.yml`；这里不存源码 checkout |
| `ECS_ENV_FILE` | `/etc/lazytt/rag.env` | 主机配置文件绝对路径；未配置时使用此默认值 |

上表统一使用仓库级配置。workflow 的部署 Job 绑定 `environment: dev`；若也在 `dev`
中设置同名项，需核对实际覆盖关系，避免连接到非预期主机。
如果服务器只允许普通用户登录，当前脚本需要先支持相应提权方式，不能只换 `ECS_USER`。

### 1.2 仓库级 Secrets

在同一 Actions 设置页的 **Secrets** 中添加下列两项。多行内容须保留实际换行。
配置入口参见 [GitHub Secrets 官方说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)。

| 名称 | 填写内容 | 用途与填写要求 |
|---|---|---|
| `ECS_SSH_PRIVATE_KEY` | `<REDACTED：完整部署私钥>` | 保留私钥首尾标记及换行；对应公钥须已在目标账号授权。当前流程没有解锁带口令私钥的步骤 |
| `ECS_KNOWN_HOSTS` | `<已核实的 known_hosts 记录>` | 服务器 SSH 主机公钥记录，供 StrictHostKeyChecking 校验；不是登录账号公钥，也不是单独的指纹 |

`ECS_KNOWN_HOSTS` 格式示意，公钥须从可信渠道核实后填写：

```text
# SSH 使用 22 端口时
<ECS_SSH_HOST> ssh-ed25519 <主机公钥的Base64内容>

# SSH 使用其他端口时
[<ECS_SSH_HOST>]:<ECS_SSH_PORT> ssh-ed25519 <主机公钥的Base64内容>
```

示例中的算法名称按服务器实际主机密钥类型填写。SSH 私钥、数据库密码及模型 Key 不放入 Variables。

### 1.3 内置凭据、镜像与手动运行参数

workflow 使用 GitHub 自动提供的 `github.token` 登录 GHCR，不需要手工新增 `GITHUB_TOKEN`
Secret。构建 Job 申请 `packages: write`，部署 Job 申请 `packages: read`。
如果 RAGFlow 镜像是私有包，还需核实该仓库 Actions 对它的读取权限；包权限设置参见
[GitHub Packages 官方说明](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility)。
当前代码不读取自定义 `GHCR_TOKEN`，仅在 Secrets 中新增它不会改变登录方式。

当前 Git remote 对应 `lazyaix/lazytt-rag-system`，默认自研镜像为
`ghcr.io/lazyaix/lazytt-rag-system@sha256:<完整digest>`。RAGFlow 镜像为
`ghcr.io/lazyaix/ragflow@sha256:<完整digest>`。两者职责不同，迁移使用自研镜像。

手动触发 `ECS backend` 时使用以下输入，它们不属于 GitHub Variables：

| 输入 | 填写方式 |
|---|---|
| `mode` | `build` 构建/核验镜像；`prepare` 拉取并准备 ECS 候选；`release` 正式更新服务 |
| `candidate_image` | 首次构建留空；复用制品时填自研镜像完整 digest |
| `candidate_revision` | 首次构建留空；复用制品时与上一项同时填写对应的 40 位 Git SHA |

`prepare` 不执行数据库迁移，也不注册账号或模型。当前 GitHub 页面没有 `migrate`、
`bootstrap-account` 等选项，这些通过第 3 节的 ECS 管理命令执行。

## 2. Docker Compose 需要的环境变量

实际值只保存到 ECS 的 `/etc/lazytt/rag.env`，由 `root:root` 持有、权限为 `0600`。
从 [.env.dev.example](.env.dev.example) 填写即可，不要把本机私有 `.env` 整份上传。
当前文件使用 Bash `export KEY=VALUE`；workflow 先 source，再让 Python 和 Docker 继承变量。

在 ECS 的 root Bash 会话加载配置：

```bash
set +x
test "$(stat -c '%U:%G:%a' /etc/lazytt/rag.env)" = root:root:600
bash -n /etc/lazytt/rag.env
source /etc/lazytt/rag.env
```

当前格式不使用 Compose 的 `--env-file` 读取。修改配置后重新 release 重建容器，
仅 restart 不会加载新值。下表的公开模型配置来自本机已验证配置，ECS 仍须验证其凭据和连通性。

### 2.11 按部署阶段填写

| 阶段 | 配置要求 |
|---|---|
| `build` | 不读取 ECS 应用环境文件 |
| `prepare` | 需要受限配置文件和有效 RAGFlow digest；数据库、模型未消费字段可尚未填写 |
| `migrate` | 仍需有效镜像 digest；rag_app 迁移读取 APP_DATABASE_DSN，rag_flow 迁移读取五个 RAGFLOW_POSTGRES 字段 |
| `init-ragflow` | 两库已完成结构与权限；PostgreSQL、Redis Stack、ES、MinIO 连接完整。新账号注册时开关设为 1 |
| `bootstrap-account` | 交互输入账号邮箱和密码；自动获取并写回 RAGFlow API Key |
| `bootstrap-models` | 有效 RAGFlow API Key 及模型配置；执行实际模型探测、RAGFlow 模型注册并写回结果 |
| `release` | 完整运行配置，包括已开启媒体与重排对应的 Key；正式运行注册开关恢复为 0 |

## 3. 当前实现：数据库文件与 ECS 手动迁移

### 3.1 文件职责

镜像实际先推送到 GHCR，再由 ECS 拉取。自研 [Dockerfile](../../Dockerfile) 将
`migrations/` 打包到 `/app/migrations`；执行迁移时使用这个候选应用镜像中的 SQL，
不需要在 ECS 安装项目 Python 依赖或保留源码仓库。

```text
migrations/
├── rag_app/
│   ├── V1.0.0__init_schema.sql
│   ├── V1.0.0__stamp_existing_schema.sql
│   └── V1.0.0__to__V1.1.0__shared_knowledge_bases.sql
└── rag_flow/
    └── V0.26.4__init_schema.sql
```

| 镜像内 SQL | 目标库 | 执行条件与作用 |
|---|---|---|
| `V1.0.0__init_schema.sql` | rag_app | 仅空库；建立 V1.0.0 基线，已有结构时拒绝覆盖 |
| `V1.0.0__stamp_existing_schema.sql` | rag_app | 经审阅的完整旧 0006 结构缺少发布元数据时，补登记 V1.0.0；不代替结构迁移 |
| `V1.0.0__to__V1.1.0__shared_knowledge_bases.sql` | rag_app | V1.0.0 升级至 V1.1.0；要求知识资源、任务、查询、反馈及幂等业务表为空 |
| `V0.26.4__init_schema.sql` | rag_flow | 仅空库；建立 RAGFlow v0.26.4 基线，不包含账号、模型或业务数据 |

配套管理 SQL 位于 [database/](database/)，这些文件不在应用镜像内，由管理员按同一
已审阅 Git SHA 在工作站 pgAdmin 执行：

| 文件 | 连接位置与职责 |
|---|---|
| `01_roles_databases.pgadmin.sql` | postgres 管理库：分 A/B/C 创建业务角色及两个数据库；不能整份包进事务；已有库核对 owner 后跳过对应 CREATE DATABASE |
| `02_database_permissions.pgadmin.sql` | 管理员分别连接 rag_app、rag_flow，各执行一次，配置本系统库和 schema 权限 |
| `03_rag_app_comments.sql` | rag_app：迁移后补充中文注释 |
| `03_rag_flow_comments.sql` | rag_flow：迁移后补充中文注释 |
| `04_verify_rag_app.sql` | rag_app：只读验证 V1.1.0 结构、对象、注释与版本 |
| `04_verify_rag_flow.sql` | rag_flow：只读验证 v0.26.4 结构、对象及注释 |
| `05_verify_database_access.sql` | postgres 管理库：核查业务角色对本系统及其他数据库的访问权限 |

业务角色密码通过管理员工具设置，不在 01 文件或镜像中保存。03、04 文件以
`lazytt_rag` 有效身份执行；管理员连接业务库后可先 `SET ROLE lazytt_rag;`，
执行完成后 `RESET ROLE;`。当前两个库共用该业务所有者。

### 3.2 迁移前必须完成的准备

1. 首次将 `ECS_DEPLOY_ENABLED=false`，防止数据库尚未准备好就自动 release。
2. 按第 1、2 节填写 GitHub 配置和 ECS 环境文件；数据库地址/密码必须对应目标 ECS 存储。
3. 在 GitHub 运行 `prepare`，构建或复用已审阅镜像并交付 ECS，记录完整 image digest 和 Git SHA。
   `candidate.json` 回执包含本次 image、revision 和 mode；默认位置为 `/opt/lazytt/lazytt-rag-system/candidate.json`。
4. 管理员备份已有目标数据库并确认可恢复；使用 01、02 SQL 完成或核实角色、建库和权限。
5. 确认数据库当前状态，按第 3.5 节选分支。不要把已有库当作空库执行初始化。

### 3.3 在本机准备并交付同版本管理文件

GitHub workflow 会清理它自己的临时脚本，所以不能假设 ECS 上还留着 release.py。
本机在项目根目录的 **Bash 会话**执行以下命令，将占位符替换为已核实参数。
这里传的是辅助脚本和模板；SQL 已在应用镜像内。

```bash
set -euo pipefail

rag_revision='<与候选镜像对应的40位Git SHA>'
rag_host='<ECS_SSH_HOST>'
rag_user='root'
rag_port='22'
rag_ssh_key='<本机部署SSH私钥路径>'

[[ "$rag_revision" =~ ^[0-9a-f]{40}$ ]]
[[ "$rag_host" =~ ^[a-zA-Z0-9.-]+$ && "$rag_user" =~ ^[a-zA-Z0-9_-]+$ ]]
[[ "$rag_port" =~ ^[0-9]+$ ]]

# 从确切提交提取文件，避免混入工作区中尚未提交的配置改动。
rag_source_dir="$(mktemp -d /tmp/rag-source.XXXXXXXX)"
git archive "$rag_revision" \
  compose.dev.yml deploy/ecs/release.py \
  deploy/ecs/ragflow/service_conf.postgres.yaml.template deploy/ecs/database \
  | tar -x -C "$rag_source_dir"

# 本机 SSH known_hosts 须已可信核实，不关闭主机校验。
rag_stage="$(ssh -i "$rag_ssh_key" -p "$rag_port" \
  -o StrictHostKeyChecking=yes "$rag_user@$rag_host" \
  'mktemp -d /tmp/rag-admin.XXXXXXXX')"
[[ "$rag_stage" =~ ^/tmp/rag-admin\.[a-zA-Z0-9]+$ ]]
scp -i "$rag_ssh_key" -P "$rag_port" -o StrictHostKeyChecking=yes \
  "$rag_source_dir/compose.dev.yml" \
  "$rag_source_dir/deploy/ecs/release.py" \
  "$rag_source_dir/deploy/ecs/ragflow/service_conf.postgres.yaml.template" \
  "$rag_user@$rag_host:$rag_stage/"

printf 'ECS 管理文件目录：%s\n' "$rag_stage"
printf '本机同版本管理 SQL 目录：%s/deploy/ecs/database\n' "$rag_source_dir"
```

记录输出的 ECS 管理文件目录。上节 01、02 和后续 03～05 管理 SQL 均使用此次提取的
同版本文件，不混用工作区中的其他版本。

### 3.4 在 ECS 定义公共命令并执行全新空库迁移

下面在 **ECS 的 root Bash 会话**执行。`rag_image` 填自研镜像，不是 RAGFlow 镜像。
`rag_revision`、镜像及上节交付文件必须来自同一次已审阅候选。

```bash
set -euo pipefail
set +x

rag_stage='/tmp/rag-admin.<上节输出的实际随机串>'
rag_directory='/opt/lazytt/lazytt-rag-system'
rag_config='/etc/lazytt/rag.env'
rag_revision='<与候选镜像对应的40位Git SHA>'
rag_image='ghcr.io/lazyaix/lazytt-rag-system@sha256:<完整digest>'

[[ "$rag_stage" =~ ^/tmp/rag-admin\.[a-zA-Z0-9]+$ ]]
[[ "$rag_revision" =~ ^[0-9a-f]{40}$ ]]
test "$(stat -c '%U:%G:%a' "$rag_config")" = root:root:600
bash -n "$rag_config"
source "$rag_config"
test -f "$rag_stage/release.py"
test -f "$rag_stage/compose.dev.yml"
test -f "$rag_stage/service_conf.postgres.yaml.template"

# 手动会话使用独立临时 Docker 登录目录；不要覆盖主机共享的登录配置。
export DOCKER_CONFIG="$rag_stage/docker"
install -d -m 700 "$DOCKER_CONFIG"
# 交互输入有权读取自研镜像和 RAGFlow 镜像的 GHCR 凭据，不把凭据写在命令行。
docker login ghcr.io --username '<GHCR用户名>'

# Bash 数组保存公共命令和参数；后续命令须在同一 Bash 会话执行。
rag_ecs=(
  python3 "$rag_stage/release.py"
  --directory "$rag_directory"
  --source-compose "$rag_stage/compose.dev.yml"
  --source-template "$rag_stage/service_conf.postgres.yaml.template"
  --image "$rag_image"
  --revision "$rag_revision"
)
```

`"${rag_ecs[@]}"` 的意思是展开上面定义的整条公共命令，不是另一个文件或 Docker 命令。
管理工具会拉取并核验候选镜像，因此手动会话仍须有有效 GHCR 登录和网络访问。

**仅当 rag_app、rag_flow 都是已建好且已授权的空库时**，依次执行下列三条命令。
每条成功后再执行下一条，任何错误都先停止排查。

```bash
# 1. 自研业务库：建立 V1.0.0 基线。
"${rag_ecs[@]}" --mode migrate --database rag_app \
  --sql V1.0.0__init_schema.sql

# 2. 自研业务库：升级至当前 V1.1.0 结构。
"${rag_ecs[@]}" --mode migrate --database rag_app \
  --sql V1.0.0__to__V1.1.0__shared_knowledge_bases.sql

# 3. RAGFlow 库：建立 v0.26.4 结构。
"${rag_ecs[@]}" --mode migrate --database rag_flow \
  --sql V0.26.4__init_schema.sql
```

工具运行临时 `rag-app-migrate` 容器，由镜像内的
`python -m rag_service.cli schema migrate --database … --file …` 执行 SQL。
无需安装 Alembic，也无需把 SQL 手工复制进运行中的 RAGFlow 容器。
`migrate` 不覆盖已有运行 `compose.yml`、不启动常驻业务服务，但会修改目标数据库。
每份 SQL 单独提交事务，不会因为后续文件失败而回滚此前已经成功的文件。

### 3.5 已有数据库如何选择命令

| 当前数据库状态 | 本次操作 |
|---|---|
| rag_app 已是完整 V1.1.0 | 跳过当前初始化和升级 SQL，复核结构与权限 |
| rag_app 是已登记 V1.0.0 | 只执行 V1.0.0 → V1.1.0 升级；有旧业务数据时该脚本会拒绝 |
| rag_app 为完整旧 0006，缺少发布元数据 | 经审阅后先运行 stamp，再按 V1.0.0 升级条件处理 |
| rag_app 早于 0006、结构不完整或版本不明 | 停止，先制定并验证对应历史升级方案 |
| rag_flow 已是完整 v0.26.4 | 跳过初始化，不重复执行 V0.26.4__init_schema.sql |
| rag_flow 是空库且角色权限已准备 | 只执行该库的 v0.26.4 初始化 |

完整旧 0006 结构、缺少发布元数据时的命令：

```bash
# 仅限上表确认适用的旧 rag_app 库；空库首次安装不要执行 stamp。
"${rag_ecs[@]}" --mode migrate --database rag_app \
  --sql V1.0.0__stamp_existing_schema.sql
```

stamp 只补登记发布基线，不会把旧业务数据转换成共享知识库数据。
当前 V1.1.0 升级遇到旧业务数据会拒绝且保留数据；不得为通过检查而直接清空真实数据，
需要另行审阅数据迁移方案。`rag_app.alembic_version` 保留历史名称，但运行期已不依赖 Alembic。

### 3.6 迁移后的注释、验收与首次发布

1. 在管理员工作站 pgAdmin 中，以 `lazytt_rag` 有效身份连接对应业务库，执行两个 03 注释 SQL。
2. 分别执行两个 04 验收 SQL，确认结构、版本、注释和归属通过。
3. 管理员连接 postgres 执行 05 访问权限核查。共享实例其他库的 PUBLIC CONNECT 若导致失败，
   由管理员另行审阅权限；本流程不批量修改其他系统数据库。
4. 首次安装才执行下方账号和模型步骤。已有运行应用不重复执行首次初始化入口。

在第 3.4 节的同一 ECS Bash 会话中，确认存储配置完整，且实际环境文件已经设置
`RAGFLOW_REGISTER_ENABLED=1`。按次序执行：

```bash
source "$rag_config"
"${rag_ecs[@]}" --mode init-ragflow

# 交互输入管理员邮箱/密码；程序自动获取或复用 API Key 并写回受限环境文件。
python3 -c 'import getpass,json; print(json.dumps({"email":getpass.getpass("邮箱（隐藏输入）："),"password":getpass.getpass("管理员密码：")}))' \
  | "${rag_ecs[@]}" --mode bootstrap-account --config-file "$rag_config"
source "$rag_config"

# 先填齐模型平台 Key；该步骤实际调用模型并可能产生少量探测费用。
"${rag_ecs[@]}" --mode bootstrap-models --config-file "$rag_config"
```

管理员在实际环境文件中把 `RAGFLOW_REGISTER_ENABLED` 改回 `0`，然后执行：

```bash
source "$rag_config"
"${rag_ecs[@]}" --mode release </dev/null
```

也可在 GitHub 手动 `release`，同时填写同一个 candidate_image 和 candidate_revision，
确保发布的是已经迁移和验收的候选。首次完成并验收后再将 `ECS_DEPLOY_ENABLED` 设为 `true`。
后续无结构变更的发布复用已保存的 RAGFlow API Key；结构升级仍需先显式迁移再 release。

手动管理会话结束时，清理本次临时登录信息：

```bash
docker logout ghcr.io >/dev/null
rm -f -- "$rag_stage/docker/config.json"
rmdir -- "$rag_stage/docker"
unset DOCKER_CONFIG
```

保留 `/opt/lazytt/lazytt-rag-system/compose.yml`、配置模板、回执、实际环境文件及项目数据卷。
本次临时辅助文件和本机提取目录在管理操作完成后可单独清理，不把服务目录当作临时目录删除。
本文命令已按代码核对；真实 ECS 的数据库迁移、账号初始化和业务验收仍需执行后确认。

## 4. 目标流程：统一交付，数据库变更完成后继续发布

### 4.1 分工与顺序

目标是让流水线负责制品交付、只读验收和应用发布，管理员在数据库变更阶段只执行
明确批准的数据库操作。管理员无需另行从本机提取文件、上传脚本、拼接镜像参数或启动业务服务。

| 顺序 | 执行方 | 工作与完成条件 |
|---|---|---|
| 1. 构建候选 | 流水线 | 固定已审阅 Git SHA，构建并推送应用镜像，取得不可变 digest |
| 2. 统一交付 | 流水线 | 拉取镜像，向 ECS 候选目录交付 Compose、迁移入口、配置模板及同版本管理/验收 SQL；生成变更计划与清单 |
| 3. 等待数据库变更 | 流水线 | 保留候选文件和当前运行服务，发布管理员操作入口，进入有时限的等待阶段 |
| 4. 执行数据库变更 | 管理员 | 根据变更计划完成适用的建库、授权、迁移和注释 SQL；保留备份及执行结果，不执行应用 release |
| 5. 只读验收 | 流水线 | 使用交付的验收 SQL 核对目标数据库版本、结构、归属、注释和访问权限；全部通过才进入下一阶段 |
| 6. 继续发布 | 流水线 | 使用同一 SHA/digest 执行应用 release，等待健康检查，记录成功或失败回执 |

继续发布以数据库实际状态通过候选版本验收为条件。等待期间只做只读检查，不自动
执行数据库变更。超时、权限不足、未知结构或验证失败时停止发布，并保留候选文件供排查。

### 4.2 拟统一交付的目录

以下是目标目录，当前 workflow 尚未生成它：

```text
/opt/lazytt/lazytt-rag-system/
├── compose.yml                         当前已发布的运行定义
└── releases/
    └── <完整Git SHA>/
        ├── compose.yml                 本次候选定义，固定镜像 digest，保留配置变量引用
        ├── release.py                  同版本迁移与发布入口
        ├── service_conf.postgres.yaml.template
        ├── manifest.json               文件校验值、Git SHA、应用/RAGFlow digest
        ├── database-change-plan.md     目标库、适用前置版本、SQL 顺序与管理员完整命令
        └── database/
            ├── 01_roles_databases.pgadmin.sql
            ├── 02_database_permissions.pgadmin.sql
            ├── 03_rag_app_comments.sql
            ├── 03_rag_flow_comments.sql
            ├── 04_verify_rag_app.sql
            ├── 04_verify_rag_flow.sql
            └── 05_verify_database_access.sql
```

结构迁移 SQL 继续来自对应应用镜像的 `/app/migrations`，交付清单同时标明这些 SQL
的路径和校验值。Compose 文件名始终为 `compose.yml`；候选目录中的文件与当前运行
文件分开保存，数据库验收之前不替换当前运行定义。
真实环境文件仍位于 `/etc/lazytt/rag.env`，不进入候选交付目录或 GitHub Artifact。
Docker 临时登录信息不进入该长期保留目录。

管理员读取流水线输出的 `database-change-plan.md`，按适用分支执行其中生成的完整命令。
命令必须固定本次目录、SHA、digest、数据库及 SQL 文件，不能在执行时漂移到其他版本。
首次安装与已有库升级分别生成计划，不对所有数据库统一执行整条初始化链。

### 4.3 当前代码与目标流程的差距

| 项目 | 当前行为 | 需要补齐的实现 |
|---|---|---|
| 文件交付 | workflow 传输 Compose 源文件、release.py 和 RAGFlow 模板至临时目录，结束后清理 | 按 SHA 持久保存候选，并一并交付管理/验收 SQL、manifest 与数据库变更计划 |
| 迁移入口 | release.py 已支持显式 migrate；管理员仍需准备辅助文件和候选参数 | 由流水线生成可直接执行的迁移命令，核对交付文件与镜像的一致性 |
| 注释及验收 SQL | 文件已在仓库中，当前主要由 pgAdmin 执行；不在应用镜像内 | 增加适合目标数据库的 SQL 执行入口；流水线自动执行只读验收，数据库变更仍由管理员执行 |
| 等待与继续 | prepare 和 release 是分别触发的模式；没有等待数据库变更的步骤 | 增加等待阶段、只读验收门禁、超时和同候选恢复逻辑，验收后自动进入 release |
| 当前运行文件 | prepare 已有文件时保留原 compose.yml | 继续保留该行为，只在候选数据库验收通过后进入发布切换 |
| 首次账号和模型 | 已有 init-ragflow、bootstrap-account、bootstrap-models，但未串入 workflow | 首次部署将它们编排到数据库验收之后；先明确账号凭据的一次性受限输入方式，自动写回 API Key；日常部署复用已有 Key |

验收 SQL 与结构迁移入口需要明确区分：现有 `migrate` 只执行镜像内允许的迁移 SQL，
不能把 03～05 文件名直接传给现有 `--sql` 参数就认为已经支持。
验证其他数据库访问权限的身份也要明确授权，不能为自动化而把实例管理员密码放入应用容器。

### 4.4 完成标准

- 管理员拿到的全部文件和命令由同一次流水线交付，文件清单可与 Git SHA、镜像 digest 对照。
- 管理员只执行变更计划中的数据库操作；不再手动复制文件、获取 RAGFlow API Key 或执行 release。
- 管理员操作前，已经完成首次环境配置、所需凭据准备与备份恢复验证。
- 数据库实际版本、结构、归属、注释及访问权限全部通过后，流水线才自动继续发布。
- 超时或中断后可以针对同一候选重新进入等待/验收阶段；已经成功的初始化 SQL 不会被自动重跑。
- 普通应用发布不隐式修改数据库；应用失败恢复不承诺撤销已经提交的数据库迁移。
- 该目标流程的代码与故障路径测试完成后，再替换第 3.3 节的手动提取和上传步骤。
